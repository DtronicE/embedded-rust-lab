# 02 - memory.x, linker scripts, startup code

## The big picture: from `main.rs` to a running MCU

```
 source ──rustc──► object files ──linker (rust-lld)──► .elf ──probe-rs──► flash
                                      ▲
                       link.x  (cortex-m-rt)   <- decides *section order*
                       memory.x (you)          <- defines FLASH / RAM *addresses and sizes*
                       device.x (PAC)          <- weak interrupt handler symbols
```

A microcontroller has **no loader and no OS**. After reset the CPU reads two words from fixed addresses and starts executing. Everything else (copying variables to RAM, zeroing memory) is *your program's* job, done by startup code that the linker scripts and `cortex-m-rt` provide.

## memory.x

```ld
MEMORY
{
  FLASH : ORIGIN = 0x08000000, LENGTH = 512K   /* non-volatile: code + constants */
  RAM   : ORIGIN = 0x20000000, LENGTH = 128K   /* volatile: variables, stack */
}
```
* `MEMORY` lists regions. Names `FLASH` and `RAM` are **required by cortex-m-rt**.
* Addresses come from the chip's reference manual "memory map" chapter.
* `build.rs` copies the file into `OUT_DIR` so the `INCLUDE memory.x` inside `link.x` can find it.
* Wrong size? Too large -> program may "fit" at link time but crash on hardware. Too small -> `region FLASH overflowed` errors.
* Optional symbols: `_stack_start` (default: end of RAM; the stack grows *downwards*).

### RP2040 specialty: BOOT2
RP2040 has *no internal flash*. The mask ROM bootloader reads the first **256 bytes** of external QSPI flash, checks a CRC32, and runs them: this "boot2" configures the QSPI interface for fast execute-in-place (XIP). So our `memory.x` has a `BOOT2` region and the program places `rp2040_boot2::BOOT_LOADER_W25Q080` there (`#[link_section = ".boot2"]`). The real vector table follows at `0x10000100`.

### ESP32 specialty
ESP32 programs are **application images** loaded by a ROM + second-stage bootloader (flash offset 0x1000/0x8000 partition table, app at 0x10000). esp-hal ships its own linker scripts (`linkall.x`) and the memory layout is hidden inside `esp-hal`, which is why there is no `memory.x` in `esp32/`. `esp_bootloader_esp_idf::esp_app_desc!()` embeds the app descriptor that the bootloader verifies. Code runs from cache-mapped external flash (IROM) and data from internal SRAM (DRAM); time-critical functions go to IRAM with `#[ram]`.

## link.x: section placement (generated by cortex-m-rt)

Key sections, in flash order:

| Section | Contents | Located in |
|---------|----------|-----------|
| `.vector_table` | initial stack pointer + exception vectors + interrupt vectors | start of FLASH |
| `.text` | machine code | FLASH |
| `.rodata` | constants, string literals | FLASH |
| `.data` | initialised `static mut`/statics | **loaded** from FLASH, **lives** in RAM |
| `.bss` | zero-initialised statics | RAM (zeroed at startup) |
| `.uninit` | `MaybeUninit` statics | RAM, untouched |

`.data` has two addresses: **LMA** (load address in flash, where the bytes are stored) and **VMA** (run address in RAM). The startup code copies LMA -> VMA.

## The vector table

On Cortex-M the first entries of flash are:

```
0x0000_0000 (aliased to FLASH start): [0] initial SP   [1] Reset  [2] NMI  [3] HardFault ...
                                       [16+] device interrupts (IRQ0, IRQ1, ...)
```
On reset the core loads `SP = word[0]`, `PC = word[1]` and starts at `Reset`. Interrupt handlers are plain functions whose addresses sit in this table. `#[interrupt]` / `#[exception]` macros give the function the exact symbol name (e.g. `TIM2`) the table expects. Unused ones default to `DefaultHandler` (a loop). The **`VTOR`** register (0xE000ED08) can point the core at a table somewhere else - this is how bootloaders hand off (modules 38-40).

## Startup code (`cortex-m-rt`)

`#[entry]` marks your `fn main() -> !`. The crate provides `Reset`:

1. Pre-init hook (`__pre_init`) - optional, e.g. disable watchdog.
2. **Zero `.bss`**, **copy `.data`** from flash to RAM.
3. Enable the FPU (on `-hf` targets).
4. Call `main()`. If main ever returns it loops forever (that is why the signature is `-> !`).

You can see it:
```bash
cargo objdump --release -- -d --disassemble-symbols=Reset
cargo size --release -- -A
```

## Why `static mut` needs care
`.data/.bss` are real shared memory, and interrupts can run at any time. Safe access patterns are in module 18 (`critical_section::Mutex`, atomics).

## Stack and heap
There is no heap unless you add an allocator. The stack lives at the top of RAM growing down; with plain `cortex-m-rt` it can silently overflow into `.bss`. `flip-link` reorders memory (stack below statics) so overflow causes a HardFault instead of silent corruption. Enable it with `linker = "flip-link"` in `.cargo/config.toml` - recommended for real projects.
